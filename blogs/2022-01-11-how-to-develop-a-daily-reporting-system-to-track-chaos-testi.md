<p>Chaos Mesh is a cloud-native chaos engineering platform that orchestrates chaos experiments on Kubernetes environments. It allows you to test the resilience of your system by simulating problems such as network faults, file system faults, and Pod faults. After each chaos experiment, you can review the testing results by checking the logs. But this is neither direct nor efficient. Therefore, I decided to develop a daily reporting system that would automatically analyze logs and generate reports. This way, it’s easy to examine the logs and identify the issues.</p>
<!-- -->
<p>In this article, I will give you some insights about how to build a daily reporting system, as well as the problems I encountered during the process and how I fixed them.</p>
<h2 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="deploy-chaos-mesh-on-kubernetes">Deploy Chaos Mesh on Kubernetes<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#deploy-chaos-mesh-on-kubernetes" title="Direct link to Deploy Chaos Mesh on Kubernetes">​</a></h2>
<p>Chaos Mesh is designed for Kubernetes, which is one of the important reasons why it can allow users to inject faults into the file system, Pod, or network for specific applications.</p>
<p>In earlier documents, Chaos Mesh offered two ways to quickly deploy a virtual Kubernetes cluster on your machine: <a class="" href="https://github.com/kubernetes-sigs/kind" rel="noopener noreferrer" target="_blank">kind</a> and <a class="" href="https://minikube.sigs.k8s.io/docs/start/" rel="noopener noreferrer" target="_blank">minikube</a>. Generally, it only takes a one-line command to deploy a Kubernetes cluster as well as install Chaos Mesh. But there are some problems:</p>
<ul>
<li class="">Starting Kubernetes clusters locally affects network-related fault types.</li>
<li class="">Users on the Chinese mainland might experience an extremely slow process to pull the Docker image or even a timeout.</li>
</ul>
<p>If you use the provided script to deploy a Kubernetes cluster using kind, all Kubernetes nodes are virtual machines (VM). This adds difficulty when you pull the image offline. To address this issue, you can deploy the Kubernetes cluster on multiple physical machines instead, with each physical machine acting as a worker node. To expedite the image pulling process, you can use the <code>docker load</code> command to load the required image in advance. Apart from the two problems above, you can install <a class="" href="https://kubernetes.io/docs/reference/kubectl/overview/" rel="noopener noreferrer" target="_blank">kubectl</a> and <a class="" href="https://helm.sh/" rel="noopener noreferrer" target="_blank">Helm</a> by following the documentation.</p>
<p>Note: For the latest installation and deployment instructions, refer to <a class="" href="https://chaos-mesh.org/docs/quick-start/" rel="noopener noreferrer" target="_blank">Chaos Mesh Quick Start</a>.</p>
<h2 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="deploy-tidb">Deploy TiDB<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#deploy-tidb" title="Direct link to Deploy TiDB">​</a></h2>
<p>The next step is to deploy TiDB on Kubernetes. I used TiDB Operator to streamline the process. For details, check out <a class="" href="https://docs.pingcap.com/tidb-in-kubernetes/stable/get-started" rel="noopener noreferrer" target="_blank">Get started with TiDB Operator in Kubernetes</a>.</p>
<p>I’d like to highlight two points in this process:</p>
<ul>
<li class="">First, install Custom Resource Definitions (CRDs) to implement different components of TiDB Operator. Otherwise, you’ll get errors when you try to install TiDB Operator.</li>
<li class="">Use <a class="" href="https://longhorn.io/" rel="noopener noreferrer" target="_blank">Longhorn</a>, a distributed block storage system for Kubernetes, to create local persistent volumes (PV) for your Kubernetes cluster. This way, you don’t have to create PVs in advance: whenever a Pod is pulled, a PV is automatically created and mounted.</li>
</ul>
<p>The biggest problem that I encountered was that pulling the image could be extremely slow when deploying the service. If the nodes in your Kubernetes cluster are virtual machines, pull the required images in advance and load them to the Docker of each machine:</p>

<h2 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="run-a-chaos-experiment">Run a chaos experiment<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#run-a-chaos-experiment" title="Direct link to Run a chaos experiment">​</a></h2>
<p>To run a chaos experiment, you have to define it first through YAML files and use <code>kubectl apply</code> to start it. In this example, I created a chaos experiment using PodChaos to simulate a Pod crashing. For detailed instructions, refer to <a class="" href="https://chaos-mesh.org/docs/run-a-chaos-experiment/" rel="noopener noreferrer" target="_blank">Run a Chaos Experiment</a>.</p>
<h2 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="generate-daily-report">Generate daily report<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#generate-daily-report" title="Direct link to Generate daily report">​</a></h2>
<h3 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="collect-logs">Collect logs<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#collect-logs" title="Direct link to Collect logs">​</a></h3>
<p>Usually, when you run chaos experiments on TiDB clusters, many errors are returned. To collect those error logs, run the <code>kubectl logs</code> command:</p>

<p>All logs generated in the past 24 hours of the specific Pod in the <code>tidb-test</code> namespace will be saved to the <code>tidb.log</code> file.</p>
<h3 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="filter-errors-and-warnings">Filter errors and warnings<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#filter-errors-and-warnings" title="Direct link to Filter errors and warnings">​</a></h3>
<p>In this step, you have to filter error messages and warning messages from logs. There are two options:</p>
<ul>
<li class="">Use text processing tools, such as awk. This requires a proficient understanding of Linux/Unix commands.</li>
<li class="">Write a script. If you’re not familiar with Linux/Unix commands, this is the better option.</li>
</ul>
<h3 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="draw-a-plot">Draw a plot<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#draw-a-plot" title="Direct link to Draw a plot">​</a></h3>
<p>For plotting, I used <a class="" href="http://www.gnuplot.info/" rel="noopener noreferrer" target="_blank">gnuplot</a>, a Linux command-line graphing utility. In the example below, I imported the pressure measurement results and created a line graph to show how queries per second (QPS) were affected when a specific Pod became unavailable. Since the chaos experiment was executed periodically, the number of QPS exhibited a pattern: it would drop abruptly and then quickly return to normal.</p>

<h3 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="generate-the-report-in-pdf">Generate the report in PDF<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#generate-the-report-in-pdf" title="Direct link to Generate the report in PDF">​</a></h3>
<p>Currently, there is no available API for generating Chaos Mesh reports or analyzing results. I decided to generate the report in PDF format so it would be readable on different browsers. In my case, I used <a class="" href="https://github.com/signintech/gopdf" rel="noopener noreferrer" target="_blank">gopdf</a>, a support library that allows users to create PDF files. It also lets me insert images or draw tables, which meets my needs.</p>
<p>To generate a daily report, I used <a class="" href="https://www.linux.org/docs/man8/cron.html" rel="noopener noreferrer" target="_blank">crond</a>, a command-line utility that executes cron jobs in the background, to execute the commands early each morning. So, when I start work, there is a daily report waiting for me.</p>
<h2 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="build-a-web-application-for-daily-reporting">Build a web application for daily reporting<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#build-a-web-application-for-daily-reporting" title="Direct link to Build a web application for daily reporting">​</a></h2>
<p>But I want to make the report more readable and accessible. Isn’t it nicer if you can check reports on a web application? At first, I wanted to add a backend API and track when the report was generated. It sounds applicable but it may be too much work since all I want is to know which report requires further troubleshooting. The exact information is shown in the file name, for example: <code>report-2021-07-09-bad.pdf</code>. Thus, the reporting system’s workload and complexity are greatly reduced.</p>
<p>Still, it is necessary to improve the backend interfaces as well as enrich the report content. But for now, a daily, workable reporting system is just fine.</p>
<p>In my case, I used <a class="" href="https://github.com/vuejs/vue" rel="noopener noreferrer" target="_blank">Vue.js</a> to scaffold the web application using a UI library <a class="" href="https://www.antdv.com/docs/vue/introduce/" rel="noopener noreferrer" target="_blank">antd</a>. After that, I updated the page content by saving the automatically generated report to the static resources folder <code>static</code>. This allows the web application to read the static reports and then render them to the front end page. For details, check out <a class="" href="https://www.antdv.com/docs/vue/use-with-vue-cli/" rel="noopener noreferrer" target="_blank">Use antd in vue-cli 3</a>.</p>

<h2 class="anchor anchorTargetHideOnScrollNavbar_fkcC" id="summary">Summary<a class="hash-link" href="https://chaos-mesh.org/blog/develop-a-daily-reporting-system/#summary" title="Direct link to Summary">​</a></h2>
<p>Chaos Mesh enables you to simulate faults that most cloud-native applications might encounter. In this article, I created a PodChaos experiment and observed that QPS in the TiDB cluster was affected when the Pod became unavailable. After analyzing the logs, I can enhance the robustness and high availability of the system. I built a web application to generate daily reports for troubleshooting and debugging. You can also customize the reports to meet your own requirements.</p>
<p>Our team is also working on a project to <a class="" href="https://github.com/DigitalChinaOpenSource/TiDB-for-PostgreSQL" rel="noopener noreferrer" target="_blank">make TiDB compatible with PostgreSQL</a>. If you are interested and want to make contributions, you are welcome to pick an issue and get started.</p>
